# Безопасность сайта ЦДУМ ПО — архитектура и план

Цель — чтобы сайт муфтията нельзя было взломать «с ходу» и чтобы при любой беде его можно было быстро восстановить. Сайт соседней организации (dumpo.ru) уже взламывали, а нашему сайту люди доверяют пожертвования и религиозные материалы.

Принципы, коротко: никому не доверять по умолчанию; минимум прав везде; несколько слоёв защиты, чтобы при обходе одного держал следующий; всё, что не нужно, выключено; бэкап, из которого реально восстанавливались.

Связанные документы: `PRODUCT.md` → «Защита и безопасность» (требования), `ROADMAP.md` → этапы 11а и 12 (чек-лист).

---

## 1. От чего защищаемся

| Угроза | Как это обычно происходит | Чем грозит |
|---|---|---|
| Захват админки | Слабый или утёкший пароль сотрудника, подбор пароля, фишинг | Подмена новостей, реквизитов сбора, удаление контента |
| Подмена реквизитов пожертвований | Через админку или прямо в базе | Деньги уходят мошенникам — самый тяжёлый удар по репутации |
| Внедрение вредоносного кода (XSS) | Через HTML старых новостей, загруженный файл, поле в админке | Заражение посетителей, кража сессии администратора |
| Уязвимость в зависимостях | Устаревшие Next.js, Payload, библиотеки | Удалённое выполнение кода на сервере |
| Взлом сервера | Открытый SSH с паролем, открытая наружу база, устаревшая ОС | Полный контроль над сайтом и данными |
| Угон домена | Захват аккаунта у регистратора, смена DNS | Сайт показывает чужую страницу, письма уходят чужим |
| Утечка секретов | `.env` в git, в чате, в скриншоте | Доступ к базе, хранилищу, подделка сессий |
| Отказ в обслуживании | Наплыв ботов, флуд форм | Сайт недоступен в Рамадан и по пятницам |
| Потеря данных | Ошибка сотрудника, сбой диска, шифровальщик | Пропадают новости и медиа за годы |

## 2. Слои защиты

```
Посетитель ──► DNS (2FA у регистратора)
          ──► nginx: HTTPS, HSTS, лимиты запросов, закрытый /admin
          ──► Next.js: заголовки и CSP, санитайзер HTML, проверка ввода
          ──► Payload: роли, доступы, блокировка после неудачных входов
          ──► Postgres (только внутренняя сеть) · S3 (запись только из приложения)
          ──► Бэкапы в отдельном месте · мониторинг и журнал входов
```

### 2.1. Люди и доступы — самый частый путь взлома
- Две роли уже есть: **администратор** (всё, включая сотрудников и настройки) и **редактор** (контент). Администраторов — 1–2 человека, не больше.
- Пароли: от 12 символов, уникальные, в менеджере паролей. Один человек — один аккаунт, общих логинов нет.
- Второй фактор для админки. Встроенного в Payload нет, варианты (выбрать до запуска):
  1. закрыть `/admin` на уровне nginx — список разрешённых IP муфтията или дополнительный пароль (basic auth);
  2. подключить TOTP-плагин для Payload (проверить живость и совместимость с текущей версией Payload перед установкой).
  Рекомендация — сразу вариант 1 (просто и надёжно), вариант 2 — если сотрудники работают из разных мест.
- Ушедший сотрудник — аккаунт удаляется в тот же день; раз в квартал — сверка списка сотрудников.
- Доступы к хостингу, домену, S3 и бэкапам — у 2–3 человек, записано, у кого какие.

### 2.2. Приложение (Next.js + Payload)
**Уже сделано**
- Заголовки безопасности и CSP для публичного сайта (`next.config.ts`): `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS в продакшене.
- Санитайзер HTML перенесённых новостей по белому списку (`src/lib/sanitize/legacyHtml.ts`, с тестами).
- Доступы Payload: публично читаются только опубликованные записи, список сотрудников видят только администраторы, роль меняет только администратор (`src/lib/cms/access.ts`, `src/collections/Users.ts`).
- Загрузки ограничены по типу: картинки — jpeg/png/webp/avif (SVG нельзя), файлы — PDF и перечисленные форматы.
- GraphQL-маршрут не подключён — меньше поверхность атаки.
- Секреты только в `.env`, в git — только `.env.example`; Dependabot и CI (линт, типы, тесты, сборка, e2e).

**Нужно доделать** (найдено при разборе кода)
- [x] `PAYLOAD_SECRET`: в продакшене приложение не запускается без секрета или с секретом короче 32 символов (`src/lib/cms/security.ts`).
- [x] `csrf` и `cors` — только домен сайта (в разработке ещё localhost).
- [x] `auth` у сотрудников задан (`staffAuth`): `maxLoginAttempts` (например, 5), `lockTime` (15 минут), `tokenExpiration` (например, 8 часов), cookie `secure` и `sameSite: "Strict"` в продакшене.
- [ ] Первый вход: хук делает первого пользователя администратором. На проде создать администратора сразу после деплоя, до открытия сайта, — иначе страницу «создать первого пользователя» может занять кто угодно.
- [x] Ограничение размера загрузок — 20 МБ. Проверка, что содержимое файла соответствует типу, — позже.
- [ ] Реквизиты пожертвований и ссылки на оплату — поля только для администратора, каждое изменение — в журнал (версии Payload) и уведомление второму ответственному.
- [ ] Формы (вопрос имаму и др., вторая очередь): проверка полей на сервере, лимит частоты, Яндекс SmartCaptcha, никакого HTML от посетителей.
- [ ] CSP для `/admin` отдельная, мягче публичной (сейчас у админки CSP нет совсем).
- [x] В CI — `pnpm audit --prod --audit-level=high`; известное исключение (`braces`, только сборка стилей) записано в `pnpm-workspace.yaml`.
- [x] Секреты не попадают в git: `scripts/check-secrets.mjs` проверяет коммит (pre-commit) и весь репозиторий (CI), см. раздел 2.8.

### 2.8. Ключи и секреты — как с ними обращаться
- Живут только в локальном `.env` на машине разработчика и в переменных окружения сервера. Файлы `.env*` (кроме `.env.example`), `*.pem`, `*.key` в git не попадают (`.gitignore`) и блокируются проверкой `pnpm secrets:check`.
- Передаются лично или через менеджер паролей с общим доступом, не через чаты, почту и скриншоты. Если ключ всё же засветился — считается скомпрометированным и заменяется.
- В репозитории только `.env.example` с пустыми значениями. В CI — заведомо фальшивые значения.
- Отдельные ключи для разработки и продакшена; продакшен-ключи есть только у 2–3 человек.
- Если ключ попал в коммит: заменить ключ (удаление из истории не спасает), затем почистить историю.

### 2.3. Пожертвования
- Карточные данные через наш сервер не проходят никогда: оплата — на странице или в виджете банка/провайдера (СБП, эквайринг).
- Уведомления об оплате от провайдера — только с проверкой подписи; сумма на сайте («кладка») обновляется только по подтверждённым платежам.
- Реквизиты на сайте сверяются с договором раз в месяц; на странице сбора — официальное название получателя, чтобы подмену было видно.

### 2.4. Сервер и сеть (этап 12)
- ОС с автообновлениями безопасности; вход по SSH только по ключу, root-вход и пароли выключены; fail2ban.
- Файрвол: снаружи открыты только 80 и 443 (и SSH — по возможности только с известных адресов).
- Приложение — в Docker под отдельным пользователем без root, файловая система контейнера только для чтения, где возможно.
- nginx перед приложением: редирект на HTTPS, TLS 1.2+, лимит запросов на `/admin`, `/api/users/login` и формы, лимит размера тела запроса.
- Postgres — только во внутренней сети, отдельный пользователь приложения с правами на свою базу (не суперпользователь); миграции — отдельным пользователем при деплое.
- S3: ключ приложения — только на свой бакет; публично — только чтение файлов; листинг бакета выключен.
- Разные секреты для разработки и продакшена; смена секретов при уходе человека с доступом.

### 2.5. Домен и DNS
- Домен оформлен на организацию, не на частное лицо; двухфакторный вход у регистратора, блокировка трансфера.
- Записи CAA (кто может выпускать сертификаты), почтовые SPF/DKIM/DMARC, чтобы от имени муфтията нельзя было рассылать письма.

### 2.6. Бэкапы и восстановление
- База — ежедневно, медиа — ежедневно (инкрементально); хранение 30 дней, раз в месяц — копия на 12 месяцев.
- Бэкапы — в другом месте, чем сервер, с другими доступами (шифровальщик или взломщик сервера не должен их удалить).
- Раз в квартал — пробное восстановление на чистый сервер, время восстановления записать.

### 2.7. Наблюдение и реакция
- Мониторинг доступности (каждые 1–5 минут) и сертификата.
- Журнал входов в админку; уведомление администратору о входе с нового устройства и о блокировке после неудачных попыток.
- Логи nginx и приложения хранятся 90 дней.

## 3. Если взломали — порядок действий
1. Перевести сайт в режим обслуживания (заглушка в nginx).
2. Сменить все пароли и секреты: `PAYLOAD_SECRET` (выкинет все сессии), БД, S3, SSH-ключи, домен.
3. Найти, как вошли: журнал входов, логи nginx, изменения в версиях документов.
4. Восстановить из последнего чистого бэкапа, обновить зависимости, закрыть дыру.
5. Проверить реквизиты пожертвований; если их меняли — сообщить жертвователям и в банк.
6. Записать, что случилось и что изменили, чтобы не повторилось.

## 4. Очерёдность

**Сейчас, в коде (не зависит от хостинга)**
1. Обязательный `PAYLOAD_SECRET` в продакшене, `serverURL`/`csrf`/`cors`.
2. Настройки входа: блокировка, срок сессии, cookie.
3. Лимит размера загрузок; защита полей реквизитов.
4. `pnpm audit` в CI.

**К запуску (нужен хостинг)**
5. Сервер, nginx, файрвол, Docker без root, закрытый Postgres.
6. Защита `/admin`: IP-список или второй пароль; лимиты частоты.
7. Бэкапы и первое пробное восстановление.
8. Мониторинг и уведомления о входах.

**С муфтиятом**
9. Кто хранит доступы и отвечает за них; на кого оформлен домен; 2FA у регистратора.
10. Обучение сотрудников: пароли, фишинг, что делать при подозрении на взлом.

**Постоянно**
- Обновления зависимостей — ежемесячно и сразу при критичных уязвимостях.
- Сверка сотрудников — раз в квартал; пробное восстановление — раз в квартал.
- Перед крупным релизом — проверка `/security-review` и внешний скан (например, OWASP ZAP по стенду).

## 5. Что нужно от муфтията
- Кто будет администратором сайта (1–2 человека) и кто — редакторами.
- Откуда сотрудники заходят в админку (офис с постоянным IP или из разных мест) — от этого зависит способ защиты `/admin`.
- На кого оформлен домен cdumpo.ru, у какого регистратора, кто имеет доступ.
- Кто отвечает за хостинг и где он.
- Кто второй ответственный, которому приходят уведомления об изменении реквизитов.
